# Ember Social — Codebase Context (read once)

Every step in this roadmap assumes you've read this file. It captures the patterns, types, and traps that recur across the codebase so individual step prompts don't have to repeat them.

## Stack

- Next.js 15 App Router, TypeScript, deployed to Vercel.
- Supabase (Postgres + Auth + RLS) for storage. Migrations in `supabase/migrations/`.
- OpenAI (`gpt-4o-mini`) for AI features via the `openai` SDK.
- Vercel Cron for scheduled jobs (configured in `vercel.json`).
- Sentry for errors (`sentry.*.config.ts`).

## Key directories

- `src/app/api/` — server endpoints (App Router route handlers).
- `src/app/dashboard/workspaces/[id]/` — agency-facing UI, slug-or-UUID in `[id]`.
- `src/app/approve/[token]/` — public client-facing approval page.
- `src/lib/` — shared server code (`publish.ts`, `gbp.ts`, `resolve-workspace.ts`, supabase clients).
- `src/lib/ai/` — AI orchestration (`rewrite-content.ts`, `newsGenerator.ts`, `strategy.ts`).
- `src/components/` — shared React components.
- `supabase/schema.sql` — current schema source of truth.
- `supabase/migrations/` — incremental migrations, numbered `00N_*.sql`.

## Supabase clients (use the right one)

From `src/lib/supabase/client.ts`:

- **`createServerSupabaseClient()`** — for server components / route handlers acting on behalf of a logged-in user. Uses cookies; if `SUPABASE_SERVICE_ROLE_KEY` is set, falls back to that (RLS bypass).
- **`createAdminClient()`** — explicit service-role client. Use in webhooks, cron jobs, and trusted server-only code where there's no user session.
- **`createClient()`** in `src/lib/supabase/client-browser.ts` — anon-key browser client. Only use for queries scoped by RLS (auth user). **Never** filter by `workspace_id` from the browser using a route param — see slug bug below.

## The slug-vs-UUID trap

Workspace URLs accept either UUID or slug: `/dashboard/workspaces/<id-or-slug>/...`. Posts (and every other workspace-scoped table) store the **UUID** as `workspace_id`.

If you query from the browser like:

```ts
.eq('workspace_id', params.id)  // ← BUG when params.id is a slug
```

…you'll get zero rows because the slug doesn't match any UUID.

**Fix pattern**: have the page call an API route, and have the API route call `resolveWorkspaceId(param)` from `src/lib/resolve-workspace.ts`. See `src/app/api/workspaces/posts/route.ts` for the canonical example.

## Key tables (read `supabase/schema.sql` for the full set)

- **`workspaces`** — `id uuid`, `slug text unique`, `name text`. Multi-tenant root.
- **`client_intelligence`** — per-workspace brand voice, target audience, do-not-post rules, key messages. Drives the AI rewriter.
- **`brand_kits`** — colors, logo, watermark, font preference.
- **`social_accounts`** — per-workspace OAuth tokens for FB/IG/GBP. `platform`, `account_id`, `account_name`, `access_token`.
- **`posts`** — the central record. Statuses: `draft | pending_approval | approved | scheduled | publishing | published | failed`. Has `scheduled_at`, `platforms text[]`, `media_urls text[]`, `last_error text` (added in migration 005).
- **`post_results`** — analytics per platform per post (currently underused — A3 fixes this).
- **`workspace_api_keys`** — for the `/api/trigger` endpoint. Hashed via `sha256`. Columns: `id, workspace_id, key_hash, label, last_used_at, created_at, revoked_at`. **Note**: there is no `name` or `key_prefix` column despite older code referencing them.
- **`media`** — exists in schema but unused. No UI yet.
- **`news_articles`** — generated by `newsGenerator.ts`, synced to client's own Supabase via news-monthly cron.

## Publishing flow (the spine — don't break it)

1. External system (Everest's `socialAction.js`) → `POST /api/trigger` with API key.
2. Trigger handler (`src/app/api/trigger/route.ts`) authenticates, runs `rewriteSocialContent()` from `src/lib/ai/rewrite-content.ts`, calls `getNextAvailableDate()` (which skips Sundays), inserts a row with `status='pending_approval'`.
3. Client opens `/approve/[token]` (or agency hits `/dashboard/workspaces/<id>/approvals`), clicks Approve → status flips to `approved`.
4. Vercel cron `/api/cron/publish-scheduled` runs every 5 min, picks up `approved` posts whose `scheduled_at <= now()`, plus any `publishing` posts with `scheduled_at` >10 min ago (stuck recovery).
5. For each post → `publishPost(postId)` from `src/lib/publish.ts` → loops over `social_accounts` for the workspace → calls platform-specific publisher (`publishToFacebook`, `publishToInstagram`).
6. On success: `status='published'`. On any error: `status='failed', last_error='...'`.

**Currently implemented platforms**: Facebook, Instagram. **Stubbed**: TikTok, YouTube, LinkedIn (throw "not yet supported"). **GBP** has OAuth + token refresh in `src/lib/gbp.ts` but isn't wired into `publish.ts` yet.

## Cron config (`vercel.json`)

```json
{
  "crons": [
    { "path": "/api/cron/news-monthly", "schedule": "0 8 1 * *" },
    { "path": "/api/cron/publish-scheduled", "schedule": "*/5 * * * *" }
  ]
}
```

**Vercel free tier** caps cron jobs at 2 per project — adding new ones may need a different approach (e.g. one dispatcher cron that fans out).

## Auth on cron routes

```ts
function authorized(req: Request): boolean {
    const ua = (req.headers.get('user-agent') || '').toLowerCase()
    if (ua.includes('vercel-cron')) return true
    const secret = process.env.CRON_SECRET
    if (!secret) return process.env.NODE_ENV !== 'production'
    return req.headers.get('authorization') === `Bearer ${secret}`
}
```

Use this exact pattern for any new cron route. Don't invent new schemes.
